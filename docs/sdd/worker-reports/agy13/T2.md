### 2. 這個檔案該用什麼療法？抽 Hook 對它適用嗎？

#### 結論：抽 Custom Hook 對它「完全不適用」，甚至是有害的。

* **為什麼抽 Hook 是錯誤療法？**
  * Hook 的核心價值是**抽象化包含 React 生命週期（state/ref/effect）的響應式邏輯**。
  * 這個元件的體質很特殊：`useState`/`useRef` 加總只有 28 個宣告（僅佔全元件行數 2%），`useEffect` 僅佔 10%。它不是因為生命週期交織而肥大。
  * 如果你為了讓行數下降，硬把 198 行的 `downloadActiveReplay` 搬進一個 `useDownloadActiveReplay`，你必須傳入 `session`, `lab`, `timeline`, `snapshot`, `figureRootRef`, `globalArtifact` 等十幾二十個參數。這只會創造出一個**披著 Hook 外皮、卻需要吃 20 個參數的怪胎函式**，既沒用到 Hook 特性，也無法脫離 React 測試環境。

#### 它真正需要的療法是「兩階段下沉」與「元件邊界切割」：

1. **下沉為「純 TypeScript 模組」（Pure Functions / Services）——消滅 300+ 行**
   * **標的**：`downloadActiveReplay` (198 行)、`downloadFigureBundle` (88 行)、`uploadFigureBundle` (16 行)。
   * **做法**：這些本質是 Bundle 打包、Payload 轉換、二進位或 JSON 匯出的純 I/O 模組。應該提取至 `*.bundle.ts` 或 `*.export.ts`。
   * **原則**：純模組只接受具備清楚型別的純資料輸入（Data In），產出 Blob 或完成上傳（Data/Promise Out），**徹底切斷對 React 元件內部 State/Ref 閉包的隨意存取**。元件內只剩一行事件呼叫。
2. **下沉為「純領域選擇器」（Domain Selectors）——消滅 100+ 行**
   * **標的**：`demoDirection` (43 行)、`clipEntries` (48 行)、`storyBeamFocus` (14 行)、`activeReplayTitle/Id` (16 行)。
   * **做法**：將多個狀態投影計算移至領域輔助檔案中，寫成無副作用的純函式（`computeDemoDirection(...)`, `buildClipEntries(...)`）。
3. **視圖分解（Component Decomposition）——消滅 200+ 行**
   * **標的**：L402-490 長達 89 行的 `ui` 物件，搭配其相鄰的 `clipPanelRef`、`replayLauncherButtonRef`、`closeActiveReplay` 與底層 355 行 JSX。
   * **做法**：這 89 行的 `ui` 是一個顯眼的「程式碼壞味道（Smell）」——它是在頂層把所有子面板要用的文字、狀態、標籤打包成一大包。這代表「回放控制面板（Replay Clip Panel）」與「主場景控制」被強行捏在同一個元件。將子面板及其專屬的回呼／按鈕 Ref 拆成專屬子元件，`ui` 物件自然瓦解。

### 3. 明確回答：把它變小會讓開發變輕鬆嗎？真正的問題是什麼？

#### 明確回答：
**單純把它「變小」（例如拆成 5 個自訂 Hook 或純粹切檔），開發絕對不會變輕鬆，只會把同一團爛泥換個抽屜放，甚至更痛苦。**
因為如果依賴關係沒切斷，原本在同一個檔案內「Ctrl+F 能找到的閉包變數」，會變成「跨越 4 個 Hook 檔案、夾帶 25 個參數傳來傳去的型別噩夢」。

#### 這個元件真正的核心問題不是「行數太大」，而是：

> **「極度的抽象層級混雜（Mixed Levels of Abstraction）」與「把 React 元件當成無成本的閉包腳本環境（Scripting Scratchpad）」。**

1. **抽象層級混雜**：
   在同一個函式範圍內，開發者的心智模型在三種極端層級反覆跳躍：
   * **系統底層／I/O 協議層**：處理 198 行的 Bundle 下載打包與二進位檔案匯出（`downloadActiveReplay`）。
   * **領域演算層**：計算 43 行的方向向量（`demoDirection`）與剪輯資料過濾（`clipEntries`）。
   * **末端 UI 裝飾層**：處理 89 行的按鈕標籤、文字拼接（`ui`）與 DOM Ref 焦點管理。
2. **閉包貪婪（Closure Greediness）**：
   之所以能寫出 198 行的內嵌函式，是因為在元件內部宣告函式「完全不需要思考介面契約」——外部有 28 個 State/Ref 和 12 個 Props，函式內部隨抓隨用。這正是導致代碼無法測試、改動牽一髮動全身的元凶。
