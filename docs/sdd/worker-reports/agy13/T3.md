### 二、 順序與風險收益評估理由

重構的紀律是「**找得到／能單獨改／能單獨測**」，嚴防「搬走 500 行但需傳入 30 個 setter 的假拆分」：

1. **順序 1（第 1 組，116 行）**：極低風險、極高純度。純輸入→輸出，抽成外部純計算函式完全不需要任何 setter 或 props 雜訊，能直接單獨寫單元測試。
2. **順序 2（第 2 組，93 行）**：低風險。`vlabRef*` 前綴表明其為邊緣附加功能（虛擬實驗室/幾何控制），與主模擬管線耦合度通常最低，邊界窄，適合作為第一個獨立 Hook/元件切入點。
3. **順序 3（第 3 組，429 行）**：中等風險、最大行數收益。包含長達 128 行與 74 行的非同步 lifecycle，雖然寫入 state，但非同步邊界標準（`cancelled`/`cached`），封裝成 `useModelLoader` 能一口氣清除 429 行最容易污染生命週期的程式碼。
4. **順序 4（第 4 組，139 行）**：中等風險。屬於底層時脈驅動，抽取為 `useSimulationClock` 可將定時器 ref 與 tick 計算隔離。
5. **順序 5（第 5 組，292 行）**：中高風險。`handleTimelineSeek`（60 行）需同時協調時脈、軌道位置與視覺跳轉，必須在時脈與資料載入穩定後再處理。
6. **順序 6（第 6 組，258 行）**：最高風險。宣告名稱直接包含 `SideEffects`、`ExperienceChange`，是典型的高維狀態連動樞紐。如果過早抽取，必定產生需要傳入大量 setter 的參數地獄，必須留到狀態圖譜釐清後才能重構。

### 三、 架構定性判定：像 `SceneRenderContent` 還是 `App`？

**明確結論：以 59 個 state 的規模與成分結構來看，這個檔案「本質上非常接近 `App`（處處碰壁）」，絕不能誤判為 `SceneRenderContent`（好抽）。**

#### 判定依據：

1. **成分結構完全不是純渲染型（不像 SceneRenderContent）**：
   - `SceneRenderContent` 能夠靠抽 useMemo 一天少 13%，是因為它的 **memo 佔了 40%**，且 state 只有 21 個，大部分邏輯是「唯讀的資料轉換/渲染投影」。
   - `AppWalkerSandbox` 的 useMemo 只有 451 行（僅佔 15.5%），大宣告中的純 useMemo 更是只有 116 行。抽光第 1 組的純計算也只動了不到 4% 的皮毛。
   - 它的主體是 **useEffect（579 行）與 useCallback（520 行）**，兩者合計近 1,100 行。這代表它不是渲染層，而是一個**巨大的狀態協調與副作用分發中樞（Orchestrator）**。

2. **59 個 State 的高維度風險**：
   - 59 個 state 遠遠偏離了 SceneRenderContent 的 21 個，更逼近 App 的 77 個。
   - 在缺乏狀態管理架構的情況下，59 個 state 散落在同一個元件內，意味著隨便一個大型 callback（如 `applyHandoverModeSideEffects`、`handleTimelineSeek`）都會讀寫 5~10 個以上的 state。

3. **危險的副作用信號**：
   - 材料中明確出現了 `applyHandoverModeSideEffects` (45 行)、`handleAppModeChange` (27 行)、`handleExperienceChange` (38 行)。這類 callback 是典型的「跨領域狀態變更膠水」，在沒有先做狀態收斂前，任何抽離嘗試都會引發連鎖反應。

### 四、 關於「循環依賴」的資訊不足宣告

雖然在狀態規模與副作用成分上它高度偏向 `App`，但**是否會像 `App` 一樣「23 個叢集裡有 10 個循環依賴」並因此處處碰壁，從目前內嵌材料中屬於【資訊不足】**。

具體缺少的關鍵依據包括：
1. **59 個 State 的拓撲分佈（State Clustering）**：不知道這 59 個 state 是各自獨立於子領域（例如 20 個純屬 VLab、15 個純屬 Timeline），還是全部被全域 callback 綁在同一個巨型狀態網中。
2. **依賴陣列（Dependency Arrays）清單**：材料中看不到各 `useEffect` 與 `useCallback` 的依賴項，無法得知是否存在 `Effect A 更新 State A → 觸發 Effect B 更新 State B → 反向觸發 Effect A` 的連鎖觸發閉環。
3. **Setter 交叉呼叫矩陣**：看不到 `applyHandoverModeSideEffects` 等高風險函式內部到底寫入了哪些 setter。

**架構操作建議**：
嚴格禁絕「按照行號直接剪下貼上到自訂 Hook」的盲動。應先從**第 1 組（純衍生計算）**與**第 2 組（封閉邊緣功能）**獲取確定收益，並在動到第 3、5、6 組前，先盤點 59 個 state 的依賴矩陣，避免重蹈 `App` 處處碰壁的覆轍。
