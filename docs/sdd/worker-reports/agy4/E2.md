我是 RWD 與無障礙審查員 **E2**。以下基於內嵌材料進行語意、可操作性與佈局架構審查：

---

### 1. 讓位元素判定與理由（教學語意與可操作性）

* **結構釐清**：
  從 JSX 第 197 行可知：`className="golden-flow-primary-cue golden-flow-axis-guide"` 是掛在**同一個 `<section>` 容器**上。因此這場碰撞實質上是「**可拖曳控制元（`golden-flow-ue-handle`）**」與「**引導提示卡（`.golden-flow-axis-guide`）**」兩者之間的空間衝突。

* **判定**：應由 **`.golden-flow-axis-guide` 讓位（縮小／緊湊化／降級次要文字）**，絕對不可讓 `golden-flow-ue-handle` 讓位。

* **理由**：
  1. **核心可操作性優先於靜態提示（WCAG 2.5.8 / 2.5.5 Target Size & Interactivity）**：
     `ue-handle` 是該教學步驟中唯一的**核心操作入口**（「向右拖曳地面 UE」）。在 320px 的極窄螢幕上，可互動元件的觸控熱區與拖曳可視性具備最高優先權。若移動或縮減 handle，將直接造成使用者無法拖曳或觸控失敗（阻礙教學流程完成）。
  2. **引導資訊可依循漸進呈現原則（Progressive Disclosure / Graceful Degradation）**：
     `axis-guide` 屬於輔助性提示（Passive Cue）。在 320px 極限空間下，卡片內的次要參數（如「固定衛星、波束中心與仰角 55°」）屬於次要脈絡，卡片本身的高度與寬度應當退縮，為下方的操作主體讓出空間。

---

### 2. 具體 SCSS 做法（依循 360px 區塊既有慣例）

在既有的 `@media (max-width: 360px)` 區塊內，比照 `trace` 與 `receipt` 的處理模式（縮小 padding、壓窄寬度、隱藏次要文字）：

1. **壓窄提示卡寬度與內距**：
   現有 `.golden-flow-axis-guide` 的 `width: min(520px, calc(100vw - 8rem))` 在 320px 下為 192px 且 `padding: 14px 18px`，佔用過多空間。應在 360px 斷點內將其 `padding` 縮減為緊湊形式（例如 `6px 10px`），並適度緊縮寬度或調整 `top`/`right` 定位，避開 UE handle 的拖曳軌道。
2. **次要說明文字降級（隱藏）**：
   比照 `[data-beat="trace"] .golden-flow-trace__note { display: none; }` 的既有慣例，將 `.golden-flow-axis-guide__header span`（即「固定衛星、波束中心與仰角 55°」）設為 `display: none`，僅保留核心指令 `strong`（「向右拖曳地面 UE」），使卡片高度大幅壓縮，消除 125×25px 的垂直/水平重疊。

### 3. 跨斷點與跨 Beat 影響評估

* **跨斷點安全性**：
  所有覆寫均嚴格封裝在 `@media (max-width: 360px)` 內，>360px 視窗完全不受影響，保留原有的 clamp 與完整排版。
* **跨 Beat 隔離性**：
  * 從 JSX 材料可見：後續的 `candidate` beat 使用 `.golden-flow-pair`（L218），`qualification` beat 使用 `.golden-flow-threshold`（L228, L236），**均未使用 `.golden-flow-axis-guide` 類別**。
  * 因此，只要 CSS 選擇器精準鎖定 `.golden-flow-axis-guide`（或遵照 beat 命名習慣加註 scope），此改動**完全不會污染或破壞其他 beat**。
  * **注意禁忌**：不可使用泛用的 `.golden-flow-primary-cue` 進行寬高或定位覆寫，否則會連帶破壞 `pair` 與 `threshold` 卡片的排版。

---

### 4. 是否存在「不動 CSS、改調閘門容忍度」的正當情況？

* **有正當依據的情況（何時該改閘門）**：
  僅當碰撞屬於**幾何邊界假陽性（False Positive）**時才合理。例如：
  * 元件的外層容器具有大面積透明 padding 或裝飾性陰影，且帶有 `pointer-events: none`。
  * 視覺上本體（墨水像素）與點擊熱區並無重疊，但單純因 `getBoundingClientRect()` 的矩形外框相交而觸發警報。
* **本案判斷（不能改閘門）**：
  本案中重疊面積高達 **125×25px**（佔 320px 螢幕寬度的近 40%），且 `axis-guide` 為實體背景卡片（`data-stage-occluder`、`z-index: 14`），`ue-handle` 為實體可操作控制項。這是**真實的視覺遮蔽與操作阻礙**，屬於嚴重的 RWD 佈局缺陷，**絕不能透過放寬閘門容忍度來掩蓋**。
