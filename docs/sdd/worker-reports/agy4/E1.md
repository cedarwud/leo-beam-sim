### 四大核心問題複核分析

#### 1. D1 有沒有把「入口消失」誤判成「功能仍活著」？
**在第 1 項發生了誤判，在第 2、3 項則是正確的。**
- **何時該推理會是錯的？** 當「被測試的對象是一個需要瀏覽器渲染的 UI 拓撲，而該拓撲在全應用中已無任何掛載點，且治理規範明文將其標記為 `retired`」時，這個推理就是錯的。
- **邊界分析**：
  - **第 3 項（正確）**：首頁入口沒了，但 `/legacy` 路由依然掛載同一個渲染器。這叫「換了載體，功能與渲染仍活著」。
  - **第 2 項（正確）**：Drawer 元件依然掛載在 `App.tsx` 的 DOM 樹中，只是缺少前置點擊觸發鏈。
  - **第 1 項（錯誤）**：`LaneExperienceBar` 在整個 `src` 中沒有任何 JSX mount，治理腳本更明文要求 App 不得 import。如果一個 E2E 閘門所測的 UI 頂層入口「永遠不會在現有拓撲中回來」，則「底層元件檔案還在」不能構成保留 Browser 閘門的理由。

#### 2. QUARANTINED 是否被濫用成「不做決定」的擋箭牌？
- **第 2 項不是濫用**：有 governance replacement-gate pin 存在（刪了會紅燈），且元件仍在 React tree 中，隔離是為了等待合法 entry route 建立，符合先例。
- **第 1 項構成實質濫用**：D1 因為看到 handoff 文件寫了「元件與 transition path 保留給內部 proof tooling」，不敢拍板退休，將「對未來的內部工具不確定」包裝成了隔離。然而目前的腳本測的是舊首頁頂層 bar 的行為，即使未來建立 proof tooling，其路由、操作路徑與 UI 結構也必然不同，舊腳本絕不可能原封不動解除隔離。

#### 3. D1 對第 5 項列出 9 組候選的誠實度與推論分析
- **D1 的誠實是完全正確且值得肯定的。**
- 從呼叫順序來看，D1 已經利用 `assertWalkerHomepage` 先行通過且 timeline 暫停的事實，排除了舊三方 join 的優先嫌疑，靜態分析已做到極致。
- 在 Playwright 中，複合同步斷言（`waitForFunction`）逾時只會拋出統一的 `TimeoutError`。沒有 runtime 報錯行號或 DOM 快照，不可能在靜態層面區分究竟是 Wait 1 的 4 種 React 過濾條件失效，還是 Wait 2 的 9 組 conjunct 之一為 false。拒絕在 9 組候選中盲猜，並提出「分段命名遙測（named diagnostics）」方案，完全符合本專案嚴禁憑空猜測的紀律。

#### 4. 是否會產生「永遠不會被解除的 quarantine」？
**會，正是第 1 項（`validate:phase-c:lane-experience-bar:browser`）。**
- 如果依 D1 建議將第 1 項標記為 QUARANTINED 並保留 npm key：
  1. 公開首頁永遠不會再 mount 該元件（ADR-002 與 governance pin 鎖死）。
  2. 該 gate 寫死在 root 等待 `[data-testid="lane-experience-bar"]`。
  3. 未來即使有內部 proof tooling，也不會是這個 gate 所寫的路徑。
- 結果就是：這個 npm key 將永久處於隔離狀態，實質等於退休，卻沒有完成清理 `package.json` 與治理清單的責任。
