# Q1：`extract-region` import 推導修正報告

## 缺陷根因

原本有兩條彼此分離、但都不完整的推導路徑：

1. 搬移程式碼中的 import capture 只追到來源 `ImportDeclaration`，之後把整句 import 原樣複製並改寫路徑。它沒有保留「實際引用的是哪個 `ImportSpecifier`」這層資訊，因此只用到 `useState` 時，也會把同句的 `useCallback`、`useEffect`、`useMemo`、`useRef` 一起帶走。
2. hook 參數與回傳介面是在擷取器中用 `checker.typeToString` 另外生成；這些新生成的型別引用沒有回流到 import 收集。因此 `HandoverRailEvent`、`ShowcaseReplayController`、`SceneLane`、`SceneSourceMode` 等名稱會出現在目標檔介面，卻不一定有 import。只有當同一整句 import 因其他 runtime 引用剛好被複製時，缺漏才會被偶然遮住。
3. `UseFullyQualifiedType` 會把由函式回傳型別推得的外部型別印成 `import("...").Type`。舊邏輯只把絕對路徑 rebase 成相對路徑，沒有把它提升成具名 type import，所以會留下 inline import type。
4. 舊 `--plan` 只驗證 AST 邊界、hook 順序、capture 與寫入拓撲；它沒有在記憶體中編譯候選目標檔。因此未解析型別仍可得到 `ready: true`，直到 execute 的 post-write `tsc` 才失敗。

## 修法

- 新增以單一 binding 為粒度的 `TargetImportRequirement`。每筆需求記錄 module、imported/local name、default/named/namespace、type-only 與來源順序；合併後重建 import，不再複製整個 statement。
- 搬走的原始 AST 以 TypeScript symbol 判斷實際引用；同句中沒有被引用的 sibling specifier 不會進目標檔。helper、JSX、hook 三條路徑都使用此精簡邏輯。
- 生成參數、回傳與 JSX prop 型別時，同時取得可讀 alias 文字與 fully-qualified 型別來源：
  - 介面使用 `Dispatch<SetStateAction<T>>`、`TimelineRailDescriptor` 等具名文字；
  - 直接來源 import 與 TypeChecker 顯示的外部 `import("module").Name` 都轉成具名 type import；
  - 相對 module specifier 仍依目標檔位置 rebase。
- hook plan 會用虛擬檔案 host 把完整候選目標加入 TypeScript program，執行 syntactic/semantic diagnostics，但不寫磁碟。缺名稱、缺 export 或缺 module 會在 plan 階段以 `UNRESOLVED_IMPORT` 拒絕；其他候選目標型別錯誤則以 `TARGET_TYPECHECK` 拒絕。
- 對 module-local、無可匯入來源的生成型別（fixture 的 `HiddenLane`），hook plan 現在回報 `ready: false` 與 `UNRESOLVED_IMPORT`。

## 兩個真實案例的結果

### 案例 1：`useLeftSidebar`

依指示沒有覆寫既存的 `src/app/useLeftSidebar.ts`。對現有檔案以 TypeScript `noUnusedLocals`／`noUnusedParameters` 做單檔 semantic diagnostics，結果為：

```text
src/app/useLeftSidebar.ts: unused-diagnostics=0
```

現有 import 僅保留實際使用的 `useState`、`Dispatch`、`SetStateAction`、`getDefaultLeftSidebarTabForMode`、`InitialRuntimeState`、`LeftSidebarTab`；沒有 inline `import(...)`。新增的合成 hook fixture 另以一個刻意含多餘 React hooks 與多餘型別的 import statement 驗證修後工具本身會精簡輸出，而非只依賴這個已人工清理的檔案。

### 案例 2：`useDirectorModes`

修後、執行前的 `--plan` 對原始範圍回報 `ready: true`，11 個參數型別已是具名形式，包括：

```text
readonly HandoverRailEvent[]
ShowcaseReplayController | null
SceneLane
SceneSourceMode
readonly LiveWalkerHandoverEvent[]
TimelineRailDescriptor
```

實際用新檔名 `src/app/useDirectorModesQ1.ts` 執行成功。工具自行修改 `src/App.tsx` 並保留新模組；`App.tsx` 從 4641 行降為 4602 行。新模組只匯入 `useMemo` 與上述 6 個實際需要的具名型別，沒有 inline import，focused unused diagnostics 為：

```text
src/app/useDirectorModesQ1.ts: unused-diagnostics=0
```

全專案 `tsc --noEmit` 綠。沒有發現案例 2 的 import 以外程式問題。

第一次 execute 嘗試在 mutation 前遇到環境層 `spawnSync ... EPERM`，工具回報 `BASELINE_TSC_FAILED` 與 `No files were changed`；當時重新核對 `App.tsx` SHA-256 仍為 `4a8e7b1c...`、4641 行、目標不存在。直接 `npm run lint` 綠後重試，抽取才正式成功。這是一次暫時性的子程序啟動失敗，不是案例 2 的程式或 import 缺陷。

## 仍然無法處理的

- `--plan` 目前仍只支援 `--shape hook`。JSX/helper 維持既有 execute + post-write `tsc` rollback 契約；特別是 JSX 的 module-local prop 型別仍會在 execute 時以 `POST_TSC_FAILED` 回滾，這是為了維持既有測試與 CLI 行為。
- hook 形狀仍只接受既有白名單的 `useState`、`useRef`、`useMemo`、`useCallback`，且既有的條件式／不連續 hook、間接寫入、循環相依限制不變。
- module-local 或函式泛型型別若不能從外部模組具名匯入，工具不會擅自 export、複製宣告或建立回指來源檔的型別循環；hook plan 會以 `UNRESOLVED_IMPORT` 拒絕。
- 由 TypeChecker 推得、但只能以非具名 default／namespace 形式表達的外部型別，目前不會猜測轉換；虛擬 target typecheck 會誠實拒絕。來源中已明確存在的 default／namespace import 則可按實際 symbol 保留。
- side-effect-only import 沒有可追蹤的 symbol，不會因區域搬移而自動複製；若區域語意依賴該副作用，仍需人工判斷。
