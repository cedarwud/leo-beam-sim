我是 Playwright 測試偵錯員 **G2**。以下為基於內嵌材料的具體分析與結論：

---

### 1. `count==render` 的「settled (paused) 幀」含義與在 `/legacy` 失敗的原因分析

#### (1) 「settled (paused) 幀」的含義
- **定義**：在模擬發生交遞脈衝（handover pulse）的瞬間，透過點擊 `[data-testid="timeline-toggle-play"]` 暫停時間軸，讓畫面渲染/佈局副作用（layout effect）收斂完成，捕獲到一幀**「邏輯上的交遞錐體數量（`s.count`）嚴格等於畫面上實際繪製的錐體 Mesh 數量（`s.rendered`）」**且兩者皆大於 0 的凍結狀態。
- 目的在於驗證：所有被邏輯觸發的 handover cones 都有對應的 3D mesh 被畫出來，無一遺漏。

#### (2) 為什麼在 `/legacy` 抓不到（時序 vs 狀態 vs 首頁依賴）
- **排除項（非首頁依賴）**：材料註解與實跑日誌證實 `/legacy` 上 `homepageVisualIdentity === false`，且 `everRendered = true`（即 `readSnap` 曾回傳 `s.rendered > 0`），代表 legacy natural-pulse carrier 在 `/legacy` 上確實存在且會繪製。
- **根本原因：時序（Timing）與暫停取樣競爭（Race Condition）**：
  1. **20x 速度與 500ms 輪詢的巨大時間差**：測試啟用了 `[data-testid="timeline-speed-20x"]`（20倍速）。500ms 的輪詢間隔在模擬時間內相當於 **10 秒**。Handover pulse 屬於短暫的過渡動畫（transient burst），當測試終於輪詢到 `lit = true` 時，該脈衝在模擬時間中可能已處於尾聲。
  2. **Pause 指令延遲 + 1500ms 的等待過長**：
     - 在偵測到 `lit = true` 後，發送 `toggle.click()` 存在 IPC/事件排程延遲，在 20x 倍速下，模擬可能已經越過交遞時間點才完成暫停。
     - 暫停後又執行了 `await page.waitForTimeout(1500)`：若該 pulse 的動畫淡出（fade-out/decay）是由真實時鐘（`requestAnimationFrame` 或 wall-clock 定時器）驅動，1.5 秒足以讓可視錐體完全淡出歸零（導致 `s.rendered === 0` 或 `s.count === 0`）。
  3. **狀態不同步與重試干擾**：若第一次 pause 時未抓到而進入下一輪，`toggle.click()` 會再次觸發（恢復播放），但若時序對不上，後續的 attempt 容易在「已播完」或「非脈衝區間」中空轉，6 次嘗試全數落空。

#### (3) 證據不足之處（如需 100% 根因定性）
- 目前材料**缺少 `readSnap(page)` 的內部實作原始碼**。
- 目前材料**缺少 pulse 動畫生命週期的消逝機制**（究竟是依賴模擬時鐘 `simTime` 還是真實時鐘 `wallClockTime` 觸發淡出/銷毀）。

### 2. 缺陷屬性判定與具體修法

#### (1) 行為缺陷 vs 測試問題判定
- **主要判定為測試採樣時序缺陷**：由於 `everRendered` 已經為 true，證明 live 運行時 cones 確實有繪製，核心渲染未壞死。
- **潛在規格盲點**：若系統規格要求「當使用者按下暫停時，必須保留當前交遞錐體供凍結檢視」，但實作卻在暫停狀態下隨真實時間淡出銷毀，這才屬於產品端的狀態保留行為缺陷。

#### (2) 具體修法（不放寬 `count > 0 && rendered > 0 && count === rendered` 斷言）
修復策略應聚焦於：**不要在超高速下盲目等待 1.5 秒，改用精準捕獲時序或在正常速度/較短等待下完成凍結採樣**。

**可替換的穩定採樣片段：**
```ts
    let everRendered = false;
    let settledOk = false;
    let settledCount = NaN;
    let settledRendered = NaN;

    for (let attempt = 0; attempt < 10 && !settledOk; attempt += 1) {
      let lit = false;
      // 以較密集的時間間隔輪詢，一抓到 pulse 立即暫停
      for (let i = 0; i < 40 && !lit; i += 1) {
        const s = await readSnap(page);
        if (s.rendered > 0) {
          everRendered = true;
          lit = true;
        }
        if (!lit) await page.waitForTimeout(150);
      }
      if (!lit) continue;

      // 立即暫停時間軸
      if (await toggle.count()) await toggle.click();

      // 縮短等待時間（給予 100~200ms 讓當前渲染幀收斂，避免 pulse 在真實時間中淡出銷毀）
      await page.waitForTimeout(200);

      const s = await readSnap(page);
      if (s.count > 0 && s.rendered > 0) {
        settledCount = s.count;
        settledRendered = s.rendered;
        settledOk = true;
        console.log(`[handover-pulse-render] settled (paused) at t=${s.t}s: count=${s.count} rendered=${s.rendered}`);
        break;
      }

      // 未成功捕獲則恢復播放繼續尋找下一個 pulse
      if (await toggle.count()) await toggle.click();
      await page.waitForTimeout(500);
    }
```

### 3. 首頁行為保護問題與補全方案

#### (1) 首頁行為是否失去保護？
- **是的，首頁（`/`）當前的交遞呈現行為完全處於無保護狀態。**

#### (2) 原因與需補全的項目
- **原因**：
  依據材料註解：
  - 首頁 `pathname === '/'` 時會設定 `homepageVisualIdentity = true`。
  - 當 `homepageVisualIdentity === true && lane === 'sinr-live'` 時，舊版的 legacy natural-pulse carrier 會被**強制抑制（suppressed）**。
  - 首頁採用的是新版「normalized accepted pair」。
  - 本閘門遷移至 `/legacy` 後，**僅保護了 `/legacy` 路由下的舊版 pulse carrier**。
- **需要補齊的保護閘門**：
  必須針對首頁（`/`）新增/維護一組專屬的端對端驗證：
  1. **首頁抑制檢查**：驗證在首頁（`pathname === '/'`）的 `sinr-live` lane 下，舊版 `data-sinr-live-cell-beam-cone-count` / legacy pulse 確實處於 suppressed 狀態。
  2. **首頁新載體檢查**：驗證交遞事件發生時，首頁的「normalized accepted pair」載體與其對應視覺元素能正確繪製並更新對應狀態。
