## 我建議的前 3 個下沉標的與理由

下沉判準遵循「**單位風險的可測性收益**（Testing ROI / Risk Ratio）」，而非單純比行數：

### 1. 第一名：`uploadFigureBundle` (L1194-1209，16 行)
* **理由（極低風險、最高即時可測性）**：
  它是標準的純解析與驗證器（Pure Parser）。行數僅 16 行，與元件內部閉包變數的牽扯最小，下沉風險幾乎為零。
* **可測性收益**：
  能以零 React 依賴，迅速針對「正常二進位」、「語法毀損」、「欄位缺漏」撰寫 100% 覆蓋率的單元測試。此項適合作為團隊切實落實「兩階段下沉」的第一把手術刀與示範範本。

### 2. 第二名：`downloadFigureBundle` (L903-990，88 行)
* **理由（與第 1 名形成「對稱閉環測試」）**：
  它是資料打包與檔案匯出的純 I/O 轉換。88 行的裸邏輯下沉後，不只能獨立驗證「輸入資料 $\rightarrow$ 產出二進位/Blob」的正確性，更關鍵的是能與第 1 名的 `uploadFigureBundle` 串聯進行 **Round-trip 測試**（Export 產生的 Blob 直接丟進 Parse，斷言資料無失真還原）。
* **可測性收益**：
  直接消除資料格式協議與檔案打包的隱性破壞，一次將匯入與匯出兩大邊界安全網建置完成。

### 3. 第三名：`downloadActiveReplay` (L992-1189，198 行)
* **理由（最大技術債單點突破，巨額可測性收益）**：
  此單一邏輯佔了整個元件近 13% 篇幅。近 200 行的序列化裸邏輯留在元件中，隨時會因為外部閉包變數的微小變動而發生靜默退化（Regression）。
* **可測性收益**：
  Replay Bundle 是 `leo-beam-sim` 的核心資料合約（Data Contract）。將其下沉為獨立純模組後，能在無瀏覽器環境下，針對多星軌道、波束增益歷史、時間軸中斷等極端情境執行完整的 Schema 驗證與邊界測試。成功後能從元件本體瞬間剃除約 200 行非 UI 雜訊，大幅降低元件認知負擔。

## 我認為這個檔案真正的問題

如果不是「太大」，這個檔案的本質病灶在於以下三點：

### 1. 抽象層級的極度坍塌（Abstraction Level Collapse）
在同一個函式作用域內，頂層的視圖呈現（如 L402 `ui` 佈局、L496 `handleDialogKeys` 對話框按鍵監聽）與最底層的資料協議封包（如 L992 長達 198 行的重播資料序列化）被**平鋪直敘地混在同一個維度**。這導致閱讀者必須在「處理點擊動畫」與「手刻檔案二進位格式」之間頻繁切換心智模型。

### 2. 濫用元件閉包作為「隱式全域公佈欄（Closure as Implicit Global State）」
此元件之所以有 55% 的裸邏輯、卻只有極少數的 Hook 宣告，並非其狀態結構單純，而是開發者**將 React 元件本體當作免傳參的作用域公佈欄**。裸邏輯不需要宣告參數，就能隨意取用外層閉包中的 20 多個 state、ref 與 props。這種作法雖然在撰寫初期「看似就手」，實質上是將無狀態的資料運算與有狀態的 React 渲染循環強行死鎖，徹底抹殺了寫單元測試的可能性。

### 3. 領域資料合約（Data Contract）外溢並受困於 UI 表現層
Replay 格式與 Figure 打包是模擬器的核心資產（Domain Assets），理論上應具備跨環境能力（未來在 CLI 工具、Node.js 批次處理、CI 回放檢驗皆可復用）。然而目前這些資料規格全被封死在一個單一的原型視圖元件（`UnifiedVisualLabPrototype`）內部。這不是「元件代碼行數過多」的單純問題，而是**系統核心資料契約被前端畫面綁架**的架構性錯位。
