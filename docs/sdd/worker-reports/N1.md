## 環的普遍程度

### 結論

23 個叢集中，依 `extract-region.ts` 的同一個「參數經區域內 initializer 遞迴依賴所選
hook 回傳值」判準，**10 個有同類循環、13 個沒有**。比例是 **10/23 = 43.5%**，不是多數，
但也絕非可忽略的 1–2 個特例。

若排除本來就不是模組的命名前綴叢集，仍有 8 個具架構意義的 M/L 叢集有環：

- M：`live`、`scene`、`teaching`、`archived`、`handover`（5/12）
- L：`walker`、`current`、`modqn`（3/5）
- N：`handle`、`homepage`（2/5；機械上有環，但不應整群抽）
- U：`omega`（0/1）

所以「先做整座 App 的一次性資料流大改」沒有被 10/23 這個數字支持；但對上述 8 個 M/L
叢集，直接反覆嘗試整群抽取也確實會徒勞，必須先逐領域整理 seam。

### 量測口徑與指令

先由分析器對整個 `App` 產出 symbol-resolved hook inventory、binding users 與宣告位置：

```bash
node --import tsx/esm scripts/refactor/analyze-closure-captures.ts \
  --file src/App.tsx --function App --project tsconfig.json
```

三份 K 報告的叢集不是連續 AST 區域，因此不能把一個 prefix 的散落宣告假裝成單一
`--start/--end`。我的作法是讀取同一個 `AnalysisContext` 所建立的 `hookCalls`、`hooks`、
`references` symbol 圖，按 K1–K3 的 23 個 prefix 投影：若一個 `useState` 的 state 名稱符合
prefix，配對 setter 一併納入。這可精確重現 K1–K3 的每個「綁定數」；例如 `archived`
為 3 個綁定、9 個使用點。

對每個叢集，從每個所選 hook call 的外部 App-local dependency 出發，沿變數 initializer
遞迴追蹤；若抵達該叢集的任一所選 binding，就標成有環。這是
`scripts/refactor/extract-region.ts:665-675` 的 `dependsOnAny`／`CYCLIC_DEPENDENCY` 判準，
不是從變數名稱猜測。另以真實案例確認現況：

```bash
node --import tsx/esm scripts/refactor/extract-region.ts \
  --shape hook --plan \
  --file src/App.tsx --start 2358 --end 2384 \
  --target src/app/useArchivedTleTimeline.ts \
  --symbol useArchivedTleTimeline --project tsconfig.json
```

結果為 exit 2、`ready: false`，唯一拒絕理由是：

```text
CYCLIC_DEPENDENCY: Parameter timelineCurrentTimeSec depends on a selected hook return,
so no legal call site can satisfy both declarations.
```

## archived 的解法選項

### 選項 A：不改資料流，拆成兩個較小的 hook seam

1. **具體改什麼**

   - 從 `src/App.tsx:L2358–2371` 抽出
     `src/app/useArchivedTleTimelineDescriptor.ts`，只持有
     `archivedTleTimelineDescriptor`。
   - 從 `src/App.tsx:L2379–2384` 抽出
     `src/app/useArchivedTlePlaybackRefs.ts`，持有兩個 ref 與當 render 的同步寫入。
   - `activeTimelineDescriptor`、`timelineDurationSec`、`timelineCurrentTimeSec` 仍留在
     `App`，位於兩個 hook call 之間。

2. **時間軸真值權威**

   不改變。`homepageCanonicalAnalysis` 仍擁有 completed archived run 的 accepted cursor；
   `timelineRailDescriptor.timeline` 仍擁有 Walker／artifact／proof 的 descriptor；`App` 內的
   `activeTimelineDescriptor` 仍是唯一的可見 timeline 選擇點。新 hook 只是 adapter，沒有
   第二個 clock、selector 或 lane decision。

3. **`--plan` 結果**

   我對目前未修改的 source 實跑以下兩個唯讀 plan，兩者皆 exit 0、`ready: true`、
   `rejectionReasons: []`：

   ```bash
   node --import tsx/esm scripts/refactor/extract-region.ts --shape hook --plan \
     --file src/App.tsx --start 2358 --end 2371 \
     --target src/app/useArchivedTleTimelineDescriptor.ts \
     --symbol useArchivedTleTimelineDescriptor --project tsconfig.json

   node --import tsx/esm scripts/refactor/extract-region.ts --shape hook --plan \
     --file src/App.tsx --start 2379 --end 2384 \
     --target src/app/useArchivedTlePlaybackRefs.ts \
     --symbol useArchivedTlePlaybackRefs --project tsconfig.json
   ```

4. **風險與閘門**

   - 功能風險最低，因為資料流完全不動。
   - 架構風險是產生兩個偏淺的模組：一個包一個 `useMemo`，一個包兩個 raw refs；caller
     仍需理解三個回傳值與它們的排序。它通過 deletion test 的程度很低，較像搬行數。
   - `src/AppWalkerSandbox.tsx:L1713–1739` 有同一份資料流；只抽 `App` 會留下雙份實作。
   - `src/app/timelineRailAuthority.test.ts` 與 `src/app/archivedTlePlayback.test.ts` 應保持綠；
     後者的 App-source regex 仍包住 playback effect，選項 A 不搬該 effect。
   - `validate:frontend:scene-lane-governance` 對 `activeTimelineDescriptor` 有字面 pin。此選項
     保留那個選擇式，但任何實作仍要先跑該 gate，確認工具產生的 call／import 沒碰到其他
     source pin。它在本輪基線已因無關的
     `liveTimelineWindowStartSec + target` 舊 pin 而 exit 1，不能把既有紅燈算成此方案造成。

### 選項 B：讓 archived-only cursor 直接跟 archived producer 同步，再抽一個 hook

1. **具體改什麼**

   在 `src/App.tsx:L2379–2380` 把 archived-only ref 的 render-time 同步來源由總入口
   `timelineCurrentTimeSec` 改成它真正使用的 archived producer：

   ```ts
   const archivedTleTimelineCurrentTimeRef = useRef(
     homepageCanonicalAnalysis.timelineCurrentTimeSec ?? 0,
   );
   archivedTleTimelineCurrentTimeRef.current =
     homepageCanonicalAnalysis.timelineCurrentTimeSec ?? 0;
   ```

   然後用既有工具把 L2358–2384 的三個 binding 一次抽到
   `src/app/useArchivedTleTimeline.ts`。資料流修改也應由一個窄的 AST codemod／tooling
   執行，不能由模型重寫整檔；codemod 後先跑 `--plan`，ready 才准真正抽取。

   此 ref 只有 archived playback effect 讀取，而該 effect 已同時受
   `isArchivedTleSceneActive` 與 `runReady` gate。archived 模式下，新值與舊值相等：
   `activeTimelineDescriptor.currentTimeSec` 正是以同一個
   `homepageCanonicalAnalysis.timelineCurrentTimeSec` 建出的 descriptor 值；Walker 模式下
   ref 的內容會不同，但沒有 active consumer。

2. **時間軸真值權威**

   不改變，而且依賴方向更清楚：

   - archived accepted time：仍由 `useHomepageCanonicalAnalysis` 的
     `timelineSelection.currentTimeSec` 擁有；
   - archived playback ref：只是 wall-clock RAF 間的 transport cursor，不升格成真值；
   - 首頁可見 timeline 選擇：仍由 `App` 的 `activeTimelineDescriptor` 擁有；
   - Walker／artifact／proof：仍走 `timelineRailDescriptor.timeline`，完全不經新 hook 決策。

   換句話說，這不是把權威搬進 hook，而是移除「Walker active time 寫入 archived-only
   ref」這條沒有 consumer 的跨 lane 邊。

3. **`--plan` 結果**

   為遵守零寫入，我用記憶體內 source overlay 只替換上述兩個 expression，然後直接呼叫
   同一支 `planHookExtraction()`；磁碟上的 `src/App.tsx` 未變。結果：

   ```text
   ready: true
   parameters: homepageCanonicalAnalysis
   returns: archivedTleTimelineDescriptor,
            archivedTleTimelineCurrentTimeRef,
            archivedTleSelectTimelineTimeRef
   rejectionReasons: []
   ```

   因此按工具現行規則，修改後整段不再被 `CYCLIC_DEPENDENCY` 拒絕。這是 plan 證據，
   不是實際 extraction、post-extraction `tsc` 或 runtime acceptance。

4. **風險與閘門**

   - 最大語意風險是 source switch 的同一 render／下一個 effect 之間是否仍使用 accepted
     archived cursor。依現有 hook/effect 排序會成立，但現有 focused tests 沒有直接斷言
     「先在 Walker 播放，再切 archived，第一個 RAF 從 accepted archived cursor 開始」。
     實作時應補一個非 browser hook/integration test 守這條。
   - `src/app/timelineRailAuthority.test.ts` 守 descriptor 的 owner、horizon、claim 與 clamp；
     `src/app/archivedTlePlayback.test.ts` 守 restart、speed 與 end clamp。兩者本輪皆 exit 0，
     但它們尚未守 source-switch/ref synchronization。
   - `scripts/validate-frontend-scene-lane-governance.ts:L680–685` 守 active descriptor 的 App
     選擇點與 archived source owner。方案刻意保留這些 expression；不應新增 archived pin
     失敗。不過該 gate 本輪基線已因另一條 Walker seek 字面 pin exit 1。
   - `validate:timeline:scrubbing` 本輪基線也已因既有 artifact seek 字面 pin exit 1；方案不改
     scrub dataset 或 seek branch，不能把該既有紅燈列為方案回歸。
   - `validate:tle-journey:browser` 與 homepage browser gates 是潛在端到端守門者，但本輪依
     規則未執行。現行受支援首頁入口對 archived 分支的可達性仍有 owner 決策，因此不能
     宣稱已有 runtime/browser acceptance。
   - `AppWalkerSandbox.tsx` 有鏡像實作。若新 hook 的目的是 locality 而不只是 P4 減行，後續
     應以 tooling 讓 sandbox 也使用同一 module；否則兩條 route 仍可漂移。

### 選項 C：保留這 100 行作為 integration seam

1. **具體改什麼**：不改 `src/App.tsx:L2358–2457`；P4 改抽其他候選。
2. **時間軸真值權威**：完全不動，風險最低。
3. **`--plan` 結果**：現況整段固定為 exit 2／`CYCLIC_DEPENDENCY`；也就是明確接受這段
   不屬於現行 hook extractor 的合法 seam，而不是反覆嘗試。
4. **風險與閘門**：不會新增紅燈，但 `App` 保留 archived timeline composition 與 RAF
   transport。這 100 行是 4,250 行的 2.35%；留下它不等於 P4 失敗。真正風險是日後有人
   為追求「零留存」又把 visible-timeline authority 搬錯地方。

## 我的建議

建議採 **選項 B**，但只在 owner 明確接受「archived-only ref 應由 archived producer 同步」
這個語意後執行。理由不是讓數字變好看，而是這條 ref 的唯一 active consumer 本來就在 archived
effect；讓 Walker 的 active cursor 在 inactive lane 寫入它，沒有行為價值，卻製造反向依賴。

選項 B 保留最關鍵的 seam：`App` 仍決定哪個 `TimelineSurfaceDescriptor` 對使用者可見。新
module 只封裝 archived descriptor 與 transport refs，沒有取得 Walker／artifact／proof 的選擇權。
而且它是一個 hook，不像選項 A 產生兩個更淺的介面。

若 owner 不願意核准那兩個 expression 的語意調整，就應選 **C**，不是 A。A 雖可立即通過
plan，但主要收益是搬行數，會增加 caller 必須理解的介面，對深度與 locality 幫助有限。

任何實作順序應為：窄 AST codemod → `extract-region.ts --plan` → owner 檢查 plan 中的
parameters/returns → 工具實際 extraction → `tsc` → focused unit tests → 既有非 browser gates；
browser gate 留給可啟動 Chromium 的環境。模型不應手寫重排整個 `App.tsx`。

## 對 P4 的意涵

10/23 不是多數，因此不應先把整個 App 提升到一個 global store 或做全域資料流翻修。正確順序是：

1. **先排除錯誤抽取單位。** `handle`、`homepage`、`request`、`reset`、`has` 是 N；其中兩個
   機械上有環也不值得解，應把各 binding 歸回真正領域。
2. **先做可證明的葉節點。** 對 13 個無此類環的叢集，再以連續 AST region 逐一跑
   `--plan`；仍要接受 `HOOK_ORDER`、write、capture 等其他拒絕，不把「無環」當 ready。
3. **對 8 個有環的 M/L 叢集，先逐領域整理一條反向邊。** 每次只處理最短 cycle path，先
   決定誰擁有真值、哪些只是 adapter/cache/ref，再跑 plan。不要一次重排所有 8 個領域。
4. **保留 composition shell。** `App` 可以、也應保留 route/lane/visible authority 的最終
   選擇點；P4 的目標是把 implementation 藏到深 module 後，不是讓 `App` 完全沒有邏輯。
5. **先修或登記既有紅基線。** 本輪 `tsc`、分析器 3/3、extractor 11/11、timeline authority
   unit、archived playback unit 都 exit 0；但兩支相關靜態 gate 已在方案前 exit 1。實作後
   必須用「既有 failure + 新 failure」差分判定，不能只看最終 exit code。

這代表 P4 可以繼續，但應是「acyclic leaf extraction」與「cyclic domain seam cleanup」兩條
工作流交錯進行，而不是 23 個 prefix 逐個硬抽，也不是先做一次未定權威的全域 state 提升。

## 我查證後發現上面背景敘述有誤的地方

有一個口徑需要修正：**23 個不是字面上的純 state 叢集，而是 hook-owned binding 的命名前綴
叢集**。它們包含 `useState` state/setter、`useRef`、`useMemo`、`useCallback`，也包含 custom
hook 的回傳 binding；例如 `handle` 全是 callback／custom-hook handler，`has` 是 derived memo。
這不影響 K1–K3 的 23 個分組，也不改變本報告的 10/23 結果，但會影響如何解讀「有環」：
它描述「若把這個 prefix 當一個 hook module 搬走」的機械障礙，不等於 23 個真正 state module
都需要資料流重構。

其餘背景敘述經本輪查證無誤：`App` 確為 4,250 行、archived 為 3 個綁定／9 個使用點，
L2358–2457 的環成立，現況 `--plan` 也確實在零寫入下拒絕。
