## 我認為最該優先抽的前 2 個，以及為什麼

### 1. `showcase`（優先級最高：零風險、高內聚、邊界極清）
- **原因**：
  1. **標準異步載入生命週期**：`showcaseArtifact`、`showcaseArtifactSource`、`showcaseLoading`、`showcaseError` 構成了最標準的資料獲取四元組，完全沒有與其他複雜的 `Ref`、鏡頭或時間軸邏輯糾纏。
  2. **空間集中且獨立**：起始行號在 L2035（遠晚於其他核心系統的 L400–L600），代表它不參與 App 初始化與 3D 引擎的開機流程，抽成 `useShowcaseArtifact` 或獨立的 `<ShowcaseModal />` 能達成即刻隔離，且回傳介面純粹，完全不會有閉包過期（stale closure）風險。

### 2. `left`（次高優先級：最純粹的 UI 容器抽離）
- **原因**：
  1. **徹底解除 Layout 狀態對 App 頂層的污染**：`leftSidebarTab` 與 `leftSidebarCollapsed` 是典型的純 UI 狀態。將其與側邊欄 JSX 一起打包為 `<LeftSidebar />` 或抽出 `useLeftSidebar()`，能以極小代價立即消除 `App` 頂層 4 個狀態綁定與對應的 handlers。
  2. **單向資料流清晰**：除了最外層 CSS Grid / Flex 寬度與 3D 畫布 resize 需要知道 `collapsed` 之外，側邊欄內部切換 Tab 完全不需要讓 `App` 重新渲染（Re-render），能有效阻斷 UI 操作引發的整頁無效重繪。

## 我認為最危險的 1 個（抽了會後悔）

### 🚨 `modqn`（19 個綁定：假模組、真雜燴，硬抽成單一 Hook 必踩雷）

- **危險核心**：
  看起來名稱都有 `modqn` 前綴，極容易誘使工程師寫出一個巨大的 `useModqn()`，但**這是一個架構陷阱**。
- **為什麼抽了會後悔**：
  1. **職責嚴重發散且具備多重副作用**：
     - `modqnDemoCameraAppliedRef` 涉及 3D 場景攝影機的操作控制。
     - `modqnVisualLayerPreset` 涉及渲染管線的圖層開關。
     - `modqnReplayVisualElapsedSec` 與 `modqnReplayVisualTimeline` 涉及時間軸播放器的逐幀推進。
     - `modqnHandoverRailEvents` 則直接與切換（Handover）子系統產生跨領域耦合。
  2. **閉包與同步地獄**：
     若將這 19 個綁定塞進同一個 Hook，該 Hook 必須同時傳入 3D Canvas Context、播放軸控制器、Handover 狀態機與 UI 狀態。這只會把 `App.tsx` 的「神元件」轉移成一個「神 Hook」，且因為內部混雜多個 `Ref`（如鏡頭標記）與高頻狀態（`ElapsedSec`），極易引發**閉包資料過期**或**高頻渲染導致 3D 畫面掉幀**。
- **正確解法**：
  禁止單一步驟整群抽出。必須先將通用播放引擎（`replay`）與切換狀態機（`handover`）獨立出來後，再將 `modqn` 依「演算法資料模型」、「播放時間軸適配器」、「3D 視覺預設層」三條路線分別拆解並提升至狀態層。
