## 我認為最該優先抽的前 2 個，以及為什麼

### 1. `archived`（TLE 歷史時間軸）
* **為什麼**：**極致的低風險與高局部性（Quick Win）**。
  在 4,250 行的巨型檔案中，`archived` 的使用範圍僅落在 L2375–L2457（跨度僅 82 行），代表它在空間上**已經自然聚集**。它的語意完全收斂在歷史 TLE 軌道的時間定位，抽成獨立 Hook 或子元件幾乎不會影響其他 4,100 多行的任何邏輯，是重構初期的破冰首選。

### 2. `manual`（手動換手動作控制器）
* **為什麼**：**狀態機語意清晰，能立即消除閉包複雜度**。
  包含 Request State、Sequence Ref（防止非同步競態）與 WasPaused Ref（互動時暫停保護）。這是一個非常標準、職責單一的「事件式操作狀態機」。將其抽成 `useManualHandoverController` 後，外部只需呼叫乾淨的 `requestHandover()` 命令，能一口氣將分散在 `App` 內的暫停防護與序列比對邏輯完全封裝。

## 我認為最危險的 1 個（抽了會後悔）

### **`homepage`**
* **為什麼**：**這是最容易讓人誤以為是模組的「偽命名空間（Fake Namespace）」**。
  它包含了高達 20 個綁定、橫跨 4,090 行。表面上都叫 `homepage*`，實際上卻混合了：
  1. UI 頂層導航（`SignalTuningMainTab`、`CanonicalTab`）
  2. 物理演算設定（`EeThresholdKbitPerJoule`）
  3. 幾何軌道投影（`RailProjection`、`RailContinuityRef`）
  4. 教學與播放事件（`TeachingActive`、`DirectorHandoverRailEvents`）

  **如果貿然抽出 `useHomepage()`，下場將是災難性的**：
  你只是把 `App.tsx` 內部的混亂移進一個新的巨型 Hook 裡，完全沒有減少任何耦合。更糟的是，原本在同一個 Component 內容易被 ESLint 檢查到的 hook dependency 與 closure 陷阱，在跨越自訂 Hook 邊界後會變得更隱晦、更難追蹤。
  
  **正確處置方式**：徹底忽視 `homepage` 這個前綴，將裡面的變數拆解歸位（例如：Tab 狀態歸入 Tab 導航層、Rail 軌道投影歸入 3D 模擬引擎、閾值設定歸入 Parameter Store），切忌整團打包。
