**Reviewer:** Senior WebGL Systems Architect (multi-agent, code-anchored + adversarially verified)
**Artifact:** `docs/showcase-master-sdd.md` (untracked draft, 156 lines)
**Scope:** Academic Rigor · WebGL Performance · SVG Data-Binding · Roadmap Soundness · Lane-Governance Collisions

## 1. Executive Summary

**Verdict: APPROVED WITH REVISIONS — DO NOT START PHASE 1 OR PHASE 4 AS WRITTEN.**

The SDD has the right *instincts* but the wrong *map*. Its visual concept (dual-axis macro tint + micro flash-on-event), its fail-closed posture (§5.2), and its viewport-decoupling rule (§5.3) are genuinely well-oriented and align with shipped governance. The feasibility of the headline 100-UE visual is high — the instanced rendering substrate already exists.

But the document was written as if `leo-beam-sim` were greenfield. It never references the four shipped truth-anchors that govern exactly the surfaces it touches: `frontend-render-governance.md` (the lane matrix + Rule#9), `modqnVisualLayers.ts` (the four-preset taxonomy), `usePlaybackControls.ts` (the source-bound `effectiveSpeed` engine), and `scene-lane-governance` validator. As a result it (a) **misrepresents a stdout-scraped, episode-coarse SSE stream as a "real-time WebSocket Rewards/Pareto/Weights" feed that the producer cannot emit** (rigor-1/2), (b) **specifies a flowchart animation bound to wall-clock React render intervals that §5.1 does not forbid as a mock** (rigor-3), and (c) **proposes four concrete lane collisions** (lane-1 through lane-5) that would ship governance violations if implemented literally.

None of this is shipped code — it is a planning-doc defect set. That is the good news: every issue is fixable by a doc rewrite *before* implementation, and most fixes *reuse* infrastructure the SDD didn't know existed. The bad news is that the two most-blocked phases (Phase 1 telemetry, Phase 4 multi-catfish) are sequenced *first* and *last* on a strictly-serial Gantt, and both have unacknowledged **cross-repo producer dependencies governed by `ntn-showcase-stack`** — not `leo-beam-sim`.

**Bottom line:** the visual platform is feasible and largely de-risked in code. The SDD must be rewritten to (1) match the committed producer telemetry contract, (2) bind every new viewport layer to the existing lane/preset/speed infrastructure with named validators, and (3) re-sequence around the real cross-repo blockers. Approve the *direction*; block implementation until §1.2/§2/§4/§5 are reconciled.

## 2. Detailed Critique per Axis

### 2.1 Academic Rigor — **CONCERNS (1 strength, 4 major, 1 minor)**

The rigor posture is correctly *stated* (§5.1 "fake numbers strictly prohibited" restates CLAUDE.md §5) but the spec contains claims its own data source cannot back, and guards that are too narrow to catch the failure modes the user explicitly fears.

- **[MAJOR] Telemetry overstated — "real-time WebSocket Rewards/Pareto/Weights" is fiction (rigor-1).** §2 mermaid (`showcase-master-sdd.md:65,53,67`) and §4.1 task 1 (`:119`) claim live Pareto points, network weights, and learning rates. Ground truth: the producer emitter (`modqn-paper-reproduction/src/modqn_training_service/progress_events.py:87-134`) is **best-effort regex scraping of subprocess stdout** emitting only episode-coarse `scalarReward/r1Mean/r2Mean/r3Mean/totalHandovers` plus a single `final:` summary. There is **no per-step loss, no Pareto front, no live weights**. `learning_rate`/`objective_weights` exist only as *input* hyperparameters (`config_writer.py:194`, `allowlist.py:28`), never emitted. Transport is **SSE, not WebSocket** (`api.py` `StreamingResponse media_type="text/event-stream"`; consumer `JobsPanel.tsx:266` opens `EventSource`). A panel labeled "real-time Pareto/loss/weights" would render empty or — far worse — get backfilled from the replay bundle, silently violating §5.1. *The §2 subgraph also misattributes the DRL engine to `ntn-sim-core` (`:44`); the training producer is `modqn-paper-reproduction`.*

- **[MAJOR] The cross-repo nature of live telemetry is unacknowledged (rigor-2 — folds into Roadmap).** §4.1 frames live telemetry as a `leo-beam-sim` frontend ingest task. The truth-owning emission lives in the sibling producer's trainer stdout format. Adding loss/Pareto/per-step channels requires changing **what the Python trainer prints** — a cross-repo change governed by `ntn-showcase-stack` authority, explicitly contradicting the committed backend SDD non-goals (§2.2 "no producer-side CLI change beyond `--output-dir`"; §12.3 "No streaming progress in v1"). The danger under delivery pressure: an implementer synthesizes the missing channels locally to hit the demo date — the exact rewrite-truth-from-display failure CLAUDE.md forbids.

- **[MAJOR] Flowchart "data flowing in real-time" is a structurally-mocked animation §5.1 does not forbid (rigor-3).** `:28` binds `stroke-dasharray/stroke-dashoffset` to "React render intervals to mimic data packages flowing... in real-time." A `setInterval`/render-clock-driven pulse is *fake motion*, not fake numbers — so it passes §5.1 while being a mock in disguise. This is precisely the "absolute visual proof, NOT hardcoded animation" failure the user demanded be avoided (`:13`), and the project's own governance already enforces the stronger rule elsewhere (`frontend-render-governance.md:211-212`: "source gap instead of fake hopping animation"). §5.1 is a genuine regression below both established governance and stated intent.

- **[MAJOR] Live-vs-replay reward provenance conflated (rigor-5 — the one CONFIRMED rigor finding).** The existing `RewardCurvePanel.tsx` renders `r1Throughput/r2Handover/r3LoadBalance` from a **post-hoc** `ModqnReplayEnvelope` tagged `paper-faithful|user-trained`. The live SSE carries differently-named episode-coarse fields. The SDD never separates the two surfaces or forbids pointing the replay panel at a "live training" label — the integrity violation in compact form. (Today's code is honestly labeled at `App.tsx:195`; the risk materializes when Phase 1 lands against this silent spec.)

- **[MINOR] Fail-closed §5.2 covers disconnect but not a stale-but-connected stream (rigor-4).** §5.2 handles disconnect (correctly mapping to the shipped `JobsPanel.tsx:312` banner). **Nuance the finding corrected:** a hung trainer is *not* a silent freeze — the server emits a 10s heartbeat (`api.py:817-829`, DB-keyed, independent of the trainer) plus a trainer-side heartbeat (`worker.py:248`). The real gap is narrower: the frontend never separates "age of last *progress* event" from "age of last *heartbeat*," so it could show frozen reward/episode as live. Fixable entirely in the 2D `JobsPanel` surface; no producer change needed.

- **[STRENGTH] Fail-closed intent, lane isolation, and source-backed principle are correctly oriented (rigor-7).** §5.1/§5.2/§5.3 restate the repo's truth-immutability rule, map onto the real fail-closed banner, and align with the `SceneTelemetry` decoupling precedent. **Keep §5 verbatim** — the rigor findings are about making these principles *enforceable* (motion, staleness, provenance), not reversing them.

### 2.2 WebGL Performance — **FEASIBLE (2 strengths, 4 minor)**

The headline 100-UE visual is already de-risked in code; the perf risks are all forward-looking architecture cautions on unbuilt features, not shipped defects.

- **[STRENGTH] 100-UE is already instanced correctly (perf-2).** `SecondaryUeInstances` (`GroundScene.tsx:142-201`) renders all non-primary UEs as one `THREE.InstancedMesh` with `setColorAt`/`instanceColor.needsUpdate` — exactly the instanced-color pattern, ~2 draw calls regardless of UE count. Only the primary UE is a separate labeled mesh. The SDD's Macro layer is feasible at 60 FPS. **Caveat:** per-UE *glow radius* cannot vary on `meshStandardMaterial` (`emissiveIntensity` is one shared scalar, `:194`) — needs `onBeforeCompile` + instanced attribute or scale-fake.

- **[MINOR] Pre-existing per-frame `setState` already re-renders the whole 100-UE tree (perf-1).** `useSimulation.ts:465` calls `setVersion(v=>v+1)` on every advancing frame, busting the `sceneFrame` memo (`:396`) → `modqnServiceMap` useMemo (`:515`) → the 100-UE `.map()` (`:755-765`) every frame the sim plays. The SDD's congestion pulse + live reward curve will *compound* this. **Mitigation:** drive the pulse via a `useFrame` instance-matrix/uniform mutation (per the `SpineParticles`/`SceneTelemetry` precedent), keep the per-slot service projection as the only React prop, and add a render-budget validator asserting `GroundScene` prop identity is stable within a slot.

- **[MINOR] "200 particles per cone" (perf-3).** **Nuance:** this is the *new* "emissive particle shader" (§4.3 `:139`), **not** a blowup of the existing 2-4-per-beam `SpineParticles` (a separate component the SDD never touches). The SDD already mandates the cap "to ensure zero WebGL stuttering." When built: one `THREE.Points`/`InstancedMesh` per cone, motion+opacity from a time uniform in a `ShaderMaterial`, scoped to the focused/Explain-Handover lane only.

- **[MINOR] Phase-4 SVGLoader+ExtrudeGeometry on 200+-element SVGs (perf-4).** Real counts are ~201 (baseline) / ~238 (multi-catfish) shapes — order-of-magnitude correct. Naive per-shape extrude → hundreds of draw calls + synchronous `ShapeUtils.triangulate` + first-frame shader-compile stall on the same frame as the planetarium. **Mitigation:** extrude only the ~18-shape training-loop flowchart; merge via `BufferGeometryUtils.mergeGeometries` (target ≤10 draw calls); warm the shader before the viewport mounts; skip `<text>`. This is a *last-phase* gated feature.

- **[MINOR] `FPSCounter` per-frame `setState` is an anti-precedent (perf-5).** `FPSCounter.tsx:14-25` `setFps` inside `useFrame` every tick — negligible alone, but a cultural precedent against F10. **Critical nuance:** the *real* dominant per-frame-setState site is `useSimulation.ts:465` (the engine's deliberate frame-publish), so any future "no setState in useFrame" lint MUST allowlist it. New HUD/readouts should follow the `SceneTelemetry` dataset/ref pattern.

- **[MINOR] Director camera lerp must reuse existing speed/slow-mo hooks (perf-6, CONFIRMED).** Lerp math is cheap; the hazard is storing interpolation `t` in React state and driving OrbitControls via per-frame props (compounding perf-1). **Mitigation:** `useFrame` loop mutating `camera.position`/`controls.target` directly (per `SceneTelemetry.tsx:176-181`), time-dilation through existing `playback.effectiveSpeed` — zero per-frame setState.

### 2.3 SVG Data-Binding — **CONCERNS (1 strength, 1 major, 5 minor)**

The chosen *primitive* (stroke-dashoffset path flow) is correct; the chosen *driver* (React render intervals) and the *implied data resolution* (per-step/ms) are both wrong.

- **[MAJOR] No ms-level per-step source exists — animating "every episode" fabricates cadence (svgbind-2).** The only live signal is coarse episode-level progress (`JobsPanel.tsx:51-65,80-100`). Per-step emission is a cross-repo producer change (F3). Animating continuous ms-level packet flow while the real signal updates once per episode (seconds-to-minutes apart) asserts a data density that does not exist → breaches §5.1. **Nuance:** the title's "ms-level" is a slight strawman — the SDD says "render intervals," not "ms"; and `JobsPanel.tsx:449-451` already renders episode-aggregated metrics, so the signal isn't *only* lifecycle. **Fix:** fire edge pulses only on real SSE event boundaries; label the loop episode-paced.

- **[MINOR] Binding dasharray to React renders contradicts the repo's own decoupling precedent (svgbind-1).** **Nuance:** §1.2 `:28` has the loose wording, but §4.1 task 4 (`:122`) *already* prescribes the correct "CSS and SVG line transitions" approach, and §4.1 validation (`:123`) requires "60 FPS without impacting the parallel 3D canvas." So the SDD's phase tasks self-correct; only the §1.2 prose needs a one-line edit. **Important correction to mitigation:** do NOT reuse the `SceneTelemetry` `useFrame` pattern — `useFrame` is `@react-three/fiber`-bound; the 2D SVG dashboard is a separate React-DOM lane with no R3F context. Use plain CSS animation or a single `rAF` loop writing `style.strokeDashoffset` on id-selected refs.

- **[MINOR] Must decimate to display cadence, with honest labeling (svgbind-3).** Even with a producer feed, sub-16ms updates are imperceptible and falsely imply granularity. Add a §4.1 clause: coalesce events to one representative frame per `rAF`; surface true underlying count when coalescing ("epoch N, +K updates"); state the dash period is a display constant, not a data-rate encoding.

- **[MINOR] State-management pattern (svgbind-4).** Correct half: forbid per-step React re-render for the dash animation (use refs+rAF). **Wrong half:** the finding recommends Zustand for episode-level state — Zustand is **not a dependency and used nowhere**. The repo's *established* coarse-state pattern is memoized React Context (`runtimeContext.ts` `ModqnEnvelopeContext`), which works precisely because it changes only at slot/episode boundaries. Reuse it; don't add a library.

- **[MINOR] The dynamic-binding layer is entirely net-new (svgbind-5).** `research-visual-lab` ships *only* static Illustrator figures (4-32KB, semantic ids, zero `data-*` hooks); animation renderer (C5) and telemetry adapter (C7) are explicitly **not implemented** and the sanitizer strips `<marker>`/`<animate>`. `leo-beam-sim` must own the entire id-resolution + ref + rAF + CSS-var + decimation + fail-closed-idle module. **Nuance:** §4.1 task 4 already places animation consumer-side, so this is under-scoping (name a net-new `svgFlowBinding` module, pin to semantic ids), not a misread of the lab as an animation surface.

- **[MINOR] Phase 1 60fps validation must measure the React-commit channel (svgbind-7, CONFIRMED).** §4.1 validation only eyeballs dash smoothness. `JobsPanel.tsx:271` `setState`s on *every* SSE message including heartbeat — a hidden re-render storm could starve the shared-rAF WebGL loop (`runtimeFrameStep.ts:494`). Assert two channels: (a) bounded React re-renders during a synthetic 60Hz SSE burst, (b) sustained 3D frame timing — reuse the existing `FPSCounter.tsx` 60-frame average via the `leo-fps-counter` testid. Heed the `validator-canvas-vs-react-attr` memory: gate the React assertion on the same DOM element's own attr.

- **[STRENGTH] CSS stroke-dashoffset is main-thread-safe and well-matched (svgbind-6).** The dasharray primitive is the right path-flow technique for these tiny 6-11-edge SVGs. **Two mechanism corrections:** (1) stroke-dashoffset is **not** compositor-only (only transform/opacity/filter are) — it triggers main-thread *paint* per frame, but trivially so for these assets; (2) precompute `getTotalLength()` once on mount, never per frame.

### 2.5 Governance Collisions (folded across axes; primary impact = Roadmap + Rigor)

The SDD **never references** `frontend-render-governance.md`, the `modqnVisualLayers.ts` preset taxonomy, the `usePlaybackControls.ts` speed engine, or the lane validator. Five collisions follow:

- **[MAJOR] Phase-4 extrusion vs Rule#1/#9 (lane-1).** **Nuance:** §1.2 `:34` already says the extrusion lives in a "secondary 3D viewport," which IS the preferred separate-surface fix; §4.4 `:147` "floating alongside the satellite planetarium" is loose compositional wording. The *genuine* gap: the SDD never adds a Lane Matrix row or extends the validator, and §4.4's validation is vague prose — a Rule#9 documentation gap on a future untracked phase, not a mandate to share the planetarium frame.

- **[MAJOR] DirectorMode vs Rule#2/#6/#8 (lane-2, CONFIRMED).** Auto-triggering a beam-cone-raising focus from *play state alone* (`:16`) is the appMode-alone proof mounting Rule#2 forbids; the standalone 0.05x is a second uncoordinated speed authority bypassing the single `effectiveSpeed → runtimeFrameStep` chain; and slow-mo on `modqn-replay-proof` would fabricate a source horizon (Rule#8). **Fix:** parameterize `HANDOVER_FOCUS_SPEED` so all speed resolves through `effectiveSpeed`; gate the cone-raise behind the explicit `[Intra/Inter-HO Focus]` buttons (`:17`), never appMode+play; reuse the `HandoverEventRail.tsx:294` `sourceOwner/horizonKind` gate.

- **[MAJOR] Macro/micro layers ignore the preset taxonomy vs Rule#3/#4/#10 (lane-3, CONFIRMED).** §3.1 keys cones/arcs on camera zoom/focus (`:82,87`), but the shipped render path gates them on the **preset** (`MainScene.tsx:576-577` from `modqnVisualLayers.ts`). Camera-keyed raising would mount 0.18 cones whenever the camera zooms — including in Baseline Faithful — and the SDD never excludes proof/artifact lanes. **Fix:** map each visual layer onto the four-preset taxonomy (macro tint→Baseline Faithful; all-serving cones→Service Allocation; focus cones+arcs→Explain Handover); DirectorMode *selects* the Explain-Handover preset rather than inventing a zoom-driven raise.

- **[MAJOR] No declared target lane; mermaid wires SimState→BeamViz/ArcViz, bypassing the render plan vs Rule#2/#9 (lane-4, CONFIRMED).** The §2 diagram (`:70-74`) routes layers from `SimState` with no lane node. A SimState→BeamViz edge ignoring the plan would activate cones on `sinr-live` (which owns its own beam visuals) and fail to disable them on proof/artifact lanes. **Fix:** state the SDD targets `modqn-live-cell-preview` only; redraw the mermaid as `SimState → resolveSceneLane → resolveSceneLaneRenderPlan → {layers}`.

- **[MAJOR] 2D dashboard is a new truth-bearing surface; §5.3 alone ≠ Rule#9 (lane-5, CONFIRMED).** The Lane Matrix (`governance.md:53-58`) and the 1049-line validator cover only the four 3D lanes; there is **no** ontology for a 2D telemetry dashboard. Without a matrix row (owner=training telemetry, must fail closed) and a validator clause (asserts no three.js imports, no `<Canvas>` on truth lanes), §5.3 is prose, not a CI gate — and the dashboard could silently fall to fabricated metrics. **Fix:** add a non-3D-surface governance section / extend Rule#9 to cover non-viewport React truth surfaces; add a structural import-assertion to the validator.

- **[STRENGTH] Dual-axis macro tint + flash-on-event is the correct default-low-density design (lane-6).** Matches Baseline Faithful's clean default (`modqnVisualLayers.ts:37-42`) and Rule#10's low-density mandate. Build on it as preset-gated overlays.

- **[MINOR] Phase ordering risks shared-surface regression (lane-7, CONFIRMED).** §4.2 wires `HandoverEventRail` row-click→Director Tour (`:131`) *before* reconciling with the existing `slowMotionFocus`/`selectClusterAndSeek` gate — risking double-fire on live lanes and mis-fire on proof lanes. Land the `effectiveSpeed`/preset reconciliation first; reuse `deriveHandoverRailSlowMotionFocus`.

## 5. Verdict

**APPROVED WITH REVISIONS — CONCERNS IN PHASE 1 AND PHASE 4; PHASE 2 BLOCKED ON GOVERNANCE RECONCILIATION.**

The visual platform is feasible and, critically, **largely de-risked by shipped code** (instanced 100-UE rendering, `effectiveSpeed`/slow-mo engine, `SceneTelemetry` decoupling, the preset taxonomy, fail-closed banner, lane validator). The SDD's core instincts — dual-axis macro/micro, fail-closed, decoupled viewports, CSS dash-flow — are sound and aligned with existing governance. **This is the strength to preserve.**

It is **not** approvable as written because it was authored blind to that infrastructure, producing one telemetry-truth misrepresentation, one motion-mock loophole, one provenance-conflation risk, and five concrete lane collisions — plus two phases sequenced first/last that each carry **unacknowledged cross-repo producer dependencies governed by `ntn-showcase-stack`, not `leo-beam-sim`.** All defects are in an untracked planning doc; none are shipped. Every one is fixable by a doc rewrite that *reuses* existing infrastructure.

**Coverage of the 9 user intents:** Well-covered and feasible — High-Density 100-UE (already baseline), Algorithm-Integration Proof (the macro/micro design is right), Dedicated Showcase Buttons (the correct gate for DirectorMode), Queue/Traffic (instanced glow is feasible), Architecture Visualization (SVG dashboard is the right surface), SVG Lab Leverage (assets are usable by id). **At risk:** (1) **Live Interactive Training** — the live loss/Pareto/weights curve the user wants does not exist at the source and is a cross-repo producer change; without Phase 0 this intent stalls or gets faked. (2) **Algorithm-Integration *Proof*** — the §1.2 render-interval flowchart animation directly undercuts the user's "absolute visual proof, NOT hardcoded animation" demand unless bound to real event payloads and §5.1 is hardened. (3) **Director Mode** — feasible only as a delta over the shipped slow-mo/`effectiveSpeed`/preset engine; the standalone controller as specified would violate lane governance. (4) **Multi-Catfish Extensibility** — the training path exists upstream but no frozen, `ntn-sim-core`-validated replay bundle does, so Phase 4b cannot be estimated yet.

**Gate to lift before implementation:** rewrite §1.2/§2/§4/§5 per the enhancements above (telemetry contract truth, lane/preset/speed binding, per-phase validators, Phase 0, hardened §5.1). Once those land, Phase 2 and Phase 3 (unblocked viz) may proceed in parallel; Phase 1 live-curve and Phase 4b gate on their named producer milestones.
